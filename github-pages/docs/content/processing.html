Processing and continuity

The fork changes how workers prepare, schedule, retry, and drain selected work. The goal is to preserve indexing progress and make work states easier to distinguish.

These notes describe source at 26873006789074c436572e7f93cfbfeb03d10398. They don't claim a current production deployment or throughput gain.

From headers to a release

  1. Read headers. Indexer workers read NNTP headers and store collection and article metadata. Early fork changes added native yEnc decoding and header-persistence checks. Later work reduced deadlocks, duplicate writes, and cancellation leaks. See #10, #18, #46, #99, #183, and #218.
  2. Prepare candidates. Collection reconciliation and candidate preparation identify files and potential releases. Bounded scans, batched writes, statement reuse, and ready-work priority let prepared work advance while slower maintenance continues. See #54, #58, #65, #129, #154, and #213.
  3. Check article evidence. Verification uses the configured full or spot-check mode, bounded scratch storage, NNTP reads, and article identity checks before publication. See release verification, #101, #169, and #212.
  4. Run additional processing. Release processing extracts useful metadata, names, fingerprints, and archive details. Claims and retry state protect concurrent attempts. More files can reopen naming work, and failed native workers preserve source NZB input. See #131, #152, #157, and #207.

Fairness, retries, and visible state

Candidate selection and maintenance use bounded turns so one queue or cleanup pass can't monopolize processing. Preparation jobs batch waiting updates and reuse prepared statements, verification workers keep claims bounded and log stop reasons, and interruption recovery restores exported processing metrics. Those mechanisms are visible in #75, #78, #132, #136, #158, #183, #212, and #213.

Queue counters and outcomes are evidence about what the scheduler considered actionable. They don't establish that processing created a release, that a payload passed verification, or that a deployment has resumed natural processing. Confirm those states separately using persisted release data, verification outcomes, and post-deployment observations.

Where Rust fits

Rust supplies selected native paths, including yEnc decoding, release-name rendering, CPU snapshot collection, and benchmark evidence tools. Article-ID fingerprinting uses native PHP: the Rust FFI and worker candidate is retained only for explicit benchmarks after failing the adoption screen. PHP still coordinates app processing and storage. A native module's presence or a passing correctness test isn't a speed result. Read the benchmark protocol for caller boundaries, gaps, and adoption criteria. Relevant changes include #10, #146, #159, #163, #173, and #187.
