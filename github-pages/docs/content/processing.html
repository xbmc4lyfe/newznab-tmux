Processing and continuity

The fork changes how workers prepare, schedule, retry, and drain selected work. The goal is to preserve indexing progress and make work states easier to distinguish.

These notes describe source at 4cd2b2f3fddff73c3df3b9a508ec3cde46f92ac7. They don't claim a current production deployment or throughput gain.

From headers to a release

  1. Read headers. Indexer workers read NNTP headers and store collection and article metadata. Early fork changes added native yEnc decoding and header-persistence checks. Later work reduced deadlocks and duplicate writes. See #10, #18, #46, and #99.
  2. Prepare candidates. Collection reconciliation and candidate preparation identify files and potential releases. Bounded scans, batched writes, and ready-work priority let prepared work advance while slower maintenance continues. See #54, #58, #65, #129, and #154.
  3. Check article evidence. Verification uses the configured full or spot-check mode, bounded scratch storage, NNTP reads, and article identity checks before publication. See release verification and #101.
  4. Run additional processing. Release processing extracts useful metadata, names, fingerprints, and archive details. Claims and retry state protect concurrent attempts. More files can reopen naming work, and failed native workers preserve source NZB input. See #131, #152, and #157.

Fairness, retries, and visible state

Candidate selection and maintenance use bounded turns so one queue or cleanup pass can't monopolize processing. Preparation jobs batch waiting updates, verification workers keep claims bounded, and interruption recovery restores exported processing metrics. Those mechanisms are visible in #75, #78, #132, #136, and #158.

Queue counters and outcomes are evidence about what the scheduler considered actionable. They don't establish that processing created a release, that a payload passed verification, or that a deployment has resumed natural processing. Confirm those states separately using persisted release data, verification outcomes, and post-deployment observations.

Where Rust fits

Rust supplies selected native paths, including yEnc decoding, release-name rendering, CPU snapshot collection, and benchmark evidence tools. Article-ID fingerprinting uses native PHP: the Rust FFI and worker candidate is retained only for explicit benchmarks after failing the adoption screen. PHP still coordinates app processing and storage. A native module's presence or a passing correctness test isn't a speed result. Read the benchmark protocol for caller boundaries, gaps, and adoption criteria. Relevant changes include #10, #146, #159, and #163.

Source anchors
