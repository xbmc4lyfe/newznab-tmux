Release identification and verification

Naming and publication answer different questions. Identification proposes what a post may be. Verification checks whether bounded article evidence supports publishing it.

All source links point to fork snapshot a4d52f4e0da633bf3bc8163e61ef6f2291f87abc. PR history records intent and review context. Current source anchors below show the behavior at that revision.

Build a release identity from evidence

Names can come from raw NNTP subjects, filenames inside NZBs and archives, PreDB catalogue titles, and PAR2 donor evidence. The fork added PreDB feed and Internet Relay Chat (IRC) sources, handling for late announcements, certified SQL filename identity projection, and matching rules for machine-generated filenames and obfuscated posts. Relevant changes include #3, #6, #7, #13, #21, #40, #124, #176, #180, and #185.

Search may discover approximate candidates, but acceptance applies stricter identity checks. Current selector policy states that backend ranking can be fuzzy while accepted title or cleaned filename identity differs only by letter case. The selector also rejects generic queries such as numeric-only names. See query eligibility. The matching service checks that candidate title/filename evidence agrees with the selected exact identity. See candidate confirmation.

Archive evidence stays bounded

RAR5 work parses bounded metadata such as file-time evidence and archived revision data, and distinguishes copy-entry checksums from target-file contents. Quick Open cache evidence is also bounded. Additional bounded metadata modules observe ISO primary descriptor copies and conditional path-table copies, gzip headers and comments, Zstandard frame and literal sizes, and XZ first-block metadata (with optional experimental Index and Footer observations). These changes improve the information available to identify contents. They don't prove that every article in a release is available or valid. See #134, #144, #166, #167, #175, #186, #189, #191, #195, #202, and #210. The detailed format code lives under docker/app/nzb-yenc-ffi/src/formats.rs and the PHP archive-processing services.

PAR2 helps identify donors

PAR2 hashes can connect an unresolved release to a known canonical title. The fork added current-inventory checks, recovery-volume fallback, donor matching, lossless descriptor provenance independent of optional file collection, and safeguards against stale or conflicting evidence. For full-hash matching, the current source checks the release snapshot and evidence generation before writing a canonical donor title. See source. Selected PRs: #73, #79, #91, #98, #118, #126, #162, and #207.

Verification gates publication

Verification reads articles through the configured source, applies full-download or spot-check rules, checks part numbers and file identity, and reports uncertainty when evidence conflicts. The candidate command only calls the publisher for passing results. Publication then rechecks the candidate version, manifest hash, and lease under a database transaction before creating or updating a release. Source: verification mode and identity checks, candidate-to-publisher handoff, and transaction and stale-claim checks.

Some imports or existing releases follow separate policies. Bounded spot checks aren't full-payload verification, and a successful source-level or test result doesn't establish that processing created a new release or is visible in search. Keep naming, evidence verdicts, persisted publication, and live search visibility as separate observations.
