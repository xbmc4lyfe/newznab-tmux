PHP-to-Rust migration

Laravel and PHP still coordinate the app. Rust handles selected operations behind explicit interfaces.

This fork builds on upstream NNTmux. The migration reflects experiments for this personal installation, not a claim that the upstream project should use a different language.

Where the languages meet

The Rust crate is docker/app/nzb-yenc-ffi. PHP calls its shared library through FFI. Some operations also use a worker executable. PHP continues to own Laravel routing, database models, queues, orchestration, and app policy. A native parser returns evidence. That doesn't by itself authorize publication or deletion.

Include the boundary cost

A fast native loop may save little when its caller spends time assembling articles, allocating buffers, converting strings, or decoding JSON. The FFI and worker paths have different costs. A worker includes its own startup and transport. A repeated FFI call has a different lifetime. Keep both in the result instead of comparing an isolated Rust loop with a complete PHP operation.

The archived Rust article-fingerprint harness measures cold and repeated operations inside fresh PHP processes. The app uses PHP fingerprinting. Its measured boundary excludes PHP process startup and autoload, but includes Rust worker startup for the worker backend. It checks independently expected digests. Full coverage adds parsed XML, incremental calls, maximum-length IDs and disk spill. Manual tail runs require at least 1,000 pairs; smaller screens leave p99 unavailable. Source pins and alternate backends turned off prevent silent backend substitution.

The source-pinned Rust fingerprint candidate performs validation, normalization, spill merging, and hashing in Rust. A future bulk FFI experiment must compare against that scalar Rust candidate and include packing, XML traversal, and cleanup. A gain over the historical PHP implementation doesn't establish headroom for another Rust replacement.

Correctness before speed

Compare results, errors, ordering, bounds, and ownership through the real caller. Malformed or incomplete evidence must keep the caller's existing failure behavior. A valid archive filename, a metadata relationship, a checksum, and verified payload bytes answer different questions. Native parsing must preserve those distinctions.

The current Rust performance contract requires at least a 1.5× gain for every common path and representative uncommon p99 workload before adoption. The published median screens don't establish that all existing native paths meet this policy. Their value is narrower: they show measured behavior and where to investigate next.

Measurement priorities

  1. Keep existing comparisons reproducible and preserve failures across architectures and run attempts.
  2. Keep archived fingerprint FFI/worker comparisons explicitly experimental and inspect CPU collector results, including cold calls, uncommon tails, and invalid observations.
  3. Use sampling results to investigate dispatch cost and large-input gains; keep failing threshold strata visible.
  4. Expand full-result baselines for archive formats and source ranges. Shared header and PAR2 projections don't establish full metadata parity.
  5. Expand common and uncommon workloads and sample counts before making p99 or adoption claims.

These priorities are open work, not promises of a particular speedup. The pull request ledger connects implemented changes to their review history.

The metadata-modules family covers article_dates, article_identity, and article_xref. The archive-modules family covers iso_primary_copies, rar5_copy_checksums, and rar5_quick_open. These comparisons use frozen source 3c647eb746. Historical feature-branch run 38719300890 completed with 48,000 eligible pairs, 96 decision rows, and zero invalid pairs. Each stratum has 1,000 pairs on each architecture. None of the 96 projection gates passed, and no production replacement was adopted. These frozen results are separate from each new main build.

The source inventory found no equivalent historical PHP implementation for these six modules. Independent, test-only PHP reference parsers read raw bytes and compute bounded shared projections. The actual final NativeMetadataParser computes richer whole outputs. Its timed boundary includes input packing, FFI allocation and copying, full native parsing, JSON copying and freeing, PHP JSON decoding, and projection. The PHP reference computes only the shared projection. Exact serialized projection parity and independent expected-output oracles gate observations; richer full native outputs are retained separately. Matching shared projections cannot establish full parser equivalence, a speedup over production PHP, or Rust adoption. adoption_qualified stays false even when projection performance gates pass.

Each family declares twelve strata with common and uncommon fixture labels. Those labels describe the experiment, not measured production frequencies. Each paired observation uses a fresh PHP process per backend, with a first call, one untimed warmup, and a repeated call. First-call cold includes FFI loading but excludes PHP process startup and autoload; it does not mean cold operating-system caches. Process elapsed time is retained separately. Randomized paired order, source/build and input identities, resource endpoints, and every failure are retained. The first invalid pair stops the run without retries; unattempted strata cannot qualify.

Qualification requires at least 1,000 independent pairs per stratum, zero invalid pairs, and stable required resource endpoints. The conservative simultaneous 95% bounds use a Bonferroni family of 48 marginal quantiles per family and architecture: twelve strata × two phases × two backends. Every common median and uncommon p99 speedup lower bound must reach 1.5× in both first-call and repeated phases to pass the projection gate. Speedup is PHP reference latency divided by native caller latency. A 31-pair screen cannot qualify p99 or adoption.

A replacement that didn't qualify

A Rust prototype moved PAR2's recursive PHP integer normalization across the FFI boundary. It preserved complete serialized output in 124 paired comparisons, including ordering, field types, and values. On x86, the two common fixtures had cold caller gains of 1.079× and 1.077×; their simultaneous interval upper bounds were 1.109× and 1.103×. Warm gains were 1.319× and 1.250×. The 31-pair screen fell below the 1.5× adoption requirement, so the existing implementation remains in use. Uncommon p99 was unavailable. This initial screen also preceded the added I/O-limit capture and can't establish qualification.

The retained screen summary records inputs, library hashes, revisions, and uncertainty. Run 38667970872 retains raw evidence for 14 days. Its source was 48ce039e43, before the prototype was removed.

Optional archive index observations

PR #202, PR #204, and PR #210 add the experimental-xz-index Cargo feature, which is off by default. It observes an immediately following, single-record Index and optional 12-byte Stream Footer after the sampled first block. It doesn't decompress payloads or validate a complete stream. The feature-gated source and correctness tests add no new public C ABI export. Neither this optional path nor the existing first-block diagnostics have an independent PHP comparison or a qualified caller benchmark.

Benchmark tools

The existing app harnesses include PHP, FFI, and worker costs. Cargo release profiles keep optimized builds explicit. Criterion and cargo-criterion can help investigate Rust kernels, while Hyperfine supports command comparisons, warmups, and JSON exports. They remain optional tools; no new dependency is required by these workflows. A kernel or command microbenchmark must still be checked through the app caller.

Check each interface's evidence

The current dashboard includes a source-derived public interface inventory, classified separately from its Rust source-file inventory. Source discovery includes experimental interfaces; an interface's presence in source doesn't establish that the selected build enables it. Caller comparisons, shared-reference projections, diagnostics, compatibility paths, lifecycle helpers, and unmeasured interfaces have different evidence boundaries. The inventory records those limits; a listed export doesn't mean it passed a performance gate.

The header-pair comparison interface has no paired benchmark. Zstd and XZ comparative gaps also remain open. The six-module study establishes shared-projection results only, with no qualified replacement. CI checks that changes to the export surface receive a coverage classification, while Pages preserves unavailable, failed, and pending measurements on each new main build.
