PHP-to-Rust migration

Laravel and PHP still coordinate the app. Rust handles selected operations behind explicit interfaces.

This fork builds on upstream NNTmux. The migration reflects experiments for this personal installation, not a claim that the upstream project should use a different language.

Where the languages meet

The Rust crate is docker/app/nzb-yenc-ffi. PHP calls its shared library through FFI. Some operations also use a worker executable. PHP continues to own Laravel routing, database models, queues, orchestration, and app policy. A native parser returns evidence. That doesn't by itself authorize publication or deletion.

Include the boundary cost

A fast native loop may save little when its caller spends time assembling articles, allocating buffers, converting strings, or decoding JSON. The FFI and worker paths have different costs. A worker includes its own startup and transport. A repeated FFI call has a different lifetime. Keep both in the result instead of comparing an isolated Rust loop with a complete PHP operation.

The article-fingerprint harness measures cold and repeated operations inside fresh PHP processes. Its measured boundary excludes PHP process startup and autoload, but includes Rust worker startup for the worker backend. It checks independently expected digests. Its sample limit doesn't support a reliable uncommon-workload p99 qualification.

Correctness before speed

Compare results, errors, ordering, bounds, and ownership through the real caller. Malformed or incomplete evidence must keep the caller's existing failure behavior. A valid archive filename, a metadata relationship, a checksum, and verified payload bytes answer different questions. Native parsing must preserve those distinctions.

The current Rust performance contract requires at least a 1.5× gain for every common path and representative uncommon p99 workload before adoption. The published median screens don't establish that all existing native paths meet this policy. Their value is narrower: they show measured behavior and where to investigate next.

Measurement priorities

  1. Keep existing comparisons reproducible and preserve failures across architectures and run attempts.
  2. Run article-ID fingerprint comparisons through both FFI and worker boundaries, and the CPU collector comparison through its command-line tool.
  3. Add a paired public-caller comparison for sampling, including dispatch thresholds, duplicates, malformed inputs, and fallback behavior.
  4. Build equivalent baseline fixtures for archive formats, PAR2 and source ranges, 7z ranges, and RAR5 variants.
  5. Expand common and uncommon workloads and sample counts before making p99 or adoption claims.

These priorities are open work, not promises of a particular speedup. The pull request ledger connects implemented changes to their review history.
