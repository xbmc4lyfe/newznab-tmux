How current evidence reaches Pages

Every rust-native push refreshes this site. Completion events from each benchmark producer refresh the same revision again as its results become available. Testing, collection, and publication use one pinned source revision. Before publishing, CI checks that rust-native still matches it. After publishing, CI checks every public file against the separately retained publication.json manifest. The manifest records the source revision, file sizes, and SHA-256 hashes. Verification allows up to 12.5 minutes for publication propagation, including the observed 10-minute cache lifetime. Stale or mismatched content still fails verification. The GitHub Pages control files .nojekyll and benchmarks/.nojekyll are excluded because they aren't served publicly.

Automatic push results remain separate from trusted manual measurements. The dashboard includes up to three recent manual runs per producer for the exact current rust-native revision, with their latest attempt identities. Runs from feature branches, other repositories, or older revisions cannot supply current measurements. A selective qualification run can appear beside a push screen without replacing it. Separate producer concurrency groups prevent manual runs from canceling pending automatic runs. Failed runs and missing artifacts remain visible. Collection is bounded; the dashboard doesn't claim to retain every manual run.

Current decoder, article-processing, and presentation measurements require complete workload matrices and frozen source, library, runtime, protocol, and report identities. Invalid counts, duplicate workloads, missing rows, and inconsistent decisions cannot qualify as complete results. Decoder reports identify the observed payload kernel. The C++ comparison retains its designated hardware requirement: an AVX2 worker cannot qualify an AVX512-VBMI2 comparison. An unsupported worker is reported explicitly.

The public Rust interface inventory lists every source-discovered FFI export, its callers, evidence family, and coverage limit. CI rejects unknown, removed, duplicate, or relocated exports until their classification is reviewed. Lifecycle helpers are included in caller timings, not separately measured gains. Compatibility interfaces and unmeasured interfaces remain explicit gaps. Source discovery doesn't expand Rust macros or evaluate conditional compilation.

Read decreases as carefully as increases

A latency speedup below 1× means the candidate took longer. A candidate-to-baseline latency ratio greater than 1 means the same thing. Don't invert one ratio and then label it with the other convention. The current dashboard preserves the harness's field names and decisions so you can check the calculation.

The frozen decoder run has no point estimate below 1×. That doesn't establish that every Rust path is faster. ARM has inconclusive rows, whole-article-body improvements are smaller, and several migrated components have no paired comparison. Current results can also fail correctness or performance gates. Those states remain in the dashboard rather than disappearing behind a successful workflow badge.

Historical CPU intervals need correction. The retained harness resamples with a linear generator followed by a modulo operation. For 1,000 observations, every resample has exactly 125 indices in each group defined by the index modulo 8. This dependence violates independent bootstrap sampling and can understate uncertainty. The recorded median and p99 point estimates remain unchanged. Preserve the raw interval fields as historical output, but don't use them as validated confidence bounds or adoption evidence. See the recorded resampling implementation.

CPU protocol version 3 replaces that historical generator with SplitMix64 and unbiased rejection sampling for pair order and bootstrap indices. It predeclares one median gate for the common fixture and one p99 gate per uncommon fixture, with 4,000 paired bootstrap replicates and simultaneous 95% Bonferroni intervals across three Linux or five macOS gates (the exact default macOS command-line tool retains both its 2× median and 1.5× p99 lower-bound requirements). Other interval fields are diagnostic per-statistic 95%. The separate exact live Linux host comparison has two simultaneous gates, median and p99, each requiring a 1.5× lower bound. Earlier version 2 intervals remain unqualified historical output. The source-pinned remaining-target study uses corrected mixed-output version 2 resampling with pointwise intervals only. Keep those source identities separate. Corrected methodology doesn't establish production adoption qualification.

A screen isn't adoption qualification

The project requires matching behavior and at least a 1.5× gain on every common path and representative uncommon p99 workload before adopting a Rust replacement under its current policy. A 5% median screen, 31-pair comparison, or green test run doesn't meet that full contract. Even a 1.9× result on one workload can't offset another required workload that fails.

Use enough observations to estimate p99, retain invalid observations separately, and record uncertainty. Don't use the maximum of a small sample as a reliable p99 estimate. Diagnostic profiles identify expensive functions. They don't supply comparable uninstrumented timings.

Reproduce an experiment

  1. Choose a frozen baseline and candidate revision. Record source and lockfile hashes, toolchains, optimized build commands, hardware, operating system, and resource limits.
  2. Use an isolated checkout and synthetic fixtures. Keep production credentials and app configuration out of the test runtime.
  3. Run correctness checks through the actual caller before comparing speed. Include errors, output ordering, and boundary costs.
  4. Use the exact workflow command and options. Preserve randomized pair order, warmup, sample counts, timeouts, and every failure.
  5. Read the run's public summary and retained raw artifacts together. Keep architecture and attempt identities separate.

Command specifications live in the yEnc workflow, the presentation workflow, and the utility workflow used for the retained run. The utility workflow specifies prebuilt binaries, 31 fingerprint pairs, and 1,000 CPU pairs. The dashboard lists coverage gaps from Rust source inventory. It doesn't treat Cargo tests as benchmarks.
