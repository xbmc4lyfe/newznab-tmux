Run the experimental fork locally

The supported quick start in this snapshot is a local Docker Compose stack. Hosted Docker deployment runbooks are separate options for existing operators.

Plan for a substantial workload. The site uses 32–64 GB RAM as a planning target for the intended personal setup. This is a recommendation, not a measured minimum, capacity test, or throughput promise. The README's supplied Compose limits total roughly 30 GiB and its MariaDB configuration sets an 8 GiB buffer pool. Adjust those settings to your host before starting.

Requirements

The fork README lists Git, just 1.43 or newer (distribution packages such as Ubuntu's 1.21 are too old), Python 3, Docker with Compose v2, and Usenet provider credentials. On macOS it names Docker Desktop or OrbStack. On Linux, Docker Engine with the Compose plugin. The supplied setup also needs adequate disk for the database, NZB storage, and verification scratch. Its example allows up to 200 GiB for verification scratch while keeping 10 GiB free. This scratch allowance is separate from the space needed for persistent data. Review the machine-readable defaults before allocating a host. See the README requirements.

ResourcePlanning targetWhy it matters

Clone the fork

git clone https://github.com/xbmc4lyfe/newznab-tmux.git
cd newznab-tmux

Configure a provider

  1. Clone the fork and enter the checkout.
  2. Create docker/config/usenet_servers.json with provider host, port, transport encryption setting, username, password, and connection count. Keep this ignored local file private and restrict its permissions.
  3. Set NNTP_PRIMARY_HOST and NNTP_ALT_HOST, then run just docker env. Set the alternate host to a separate provider only when you have configured one.
  4. Review generated docker/.env and docker/config/app.env. These contain secrets, generated app and database passwords, memory limits, and optional metadata keys.

Create docker/config/usenet_servers.json in your editor with your own provider values:

{
  "usenet_servers": [
    {
      "host": "news.example.com",
      "port": 563,
      "ssl": true,
      "username": "YOUR_USERNAME",
      "password": "YOUR_PASSWORD",
      "connections": 10
    }
  ]
}
chmod 600 docker/config/usenet_servers.json
export NNTP_PRIMARY_HOST=news.example.com
export NNTP_ALT_HOST="$NNTP_PRIMARY_HOST"
just docker env

Replace the sample host and credentials before running the commands. If you use a separate fallback provider, add its server object and set NNTP_ALT_HOST to that server's host. The generated docker/.env and docker/config/app.env contain secrets. Keep them private. Review ports, Docker VM memory limits, and app settings before initialization. The commands follow the current Justfile and docker/Justfile. The provider setup was originally recorded in this earlier README revision. The Compose stack uses bind-mounted persistent state under docker/data/.

Review processing settings first

Seeded defaults enable starter groups and configure 12 header workers, 30 backfill workers, 16 additional-processing workers, and 4 information-file workers. The README warns that the JSON connection count doesn't reduce those worker counts. Lower the database seed values to fit your provider's connection allowance, hardware, and terms before initialization. Initialization starts indexing automatically. See the README's tuning warning.

Initialize a fresh installation

just docker init DEPLOY_BY=local-setup
just docker ps

This builds the images, initializes MariaDB and search tables, installs monitoring, seeds groups and tuning, attempts a PreDB import, and starts the stack. Open http://localhost:8080. Find the generated administrator password in docker/config/app.env. Read it locally with rg '^ADMIN_PASS=' docker/config/app.env. The initializer skips installation when the persistent install lock already exists. Read the first-run notes before retrying a partial install.

Update an initialized local stack

Back up MariaDB and separately preserve configuration, NZB/storage files, and other state you need for recovery. The database backup target doesn't cover those files. Update the checkout only after preserving local changes, then use the guarded deployment:

just docker backup
just deploy-plan
just deploy

To deploy or recreate a single component without touching unrelated services, pass the component name to just deploy or use its shortcut recipe:

just deploy web          # or: just deploy-web
just deploy horizon      # or: just deploy-horizon
just deploy scheduler    # or: just deploy-scheduler
just deploy indexer      # or: just deploy-indexer
just deploy proxy        # or: just deploy-proxy
just deploy monitoring   # or: just deploy-monitoring
just deploy redis        # or: just deploy-redis
just deploy manticore    # or: just deploy-manticore

The deploy recipe serializes deployments and builds while services are live. Commits that can't change an image (documentation, tests, and files outside the Docker build context) are skipped. Otherwise it rebuilds only the affected role images and recreates only those app services. A change confined to one role (for example Vite assets for web) leaves the other writers running. For a shared PHP or configuration change it stops Horizon first, so its active jobs finish while the scheduler and indexer keep queueing work, then drains the scheduler and indexer and recreates the four app services after health checks. Every app writer is stopped before migrations, which run when a migration changed, when a Compose change reaches all four app services (for example a database cutover or an edit to the mounted docker/config/app.env), or when an otherwise unexplained Compose change requires it. A changed stateful data service stops every writer before it is recreated. A changed mounted configuration file recreates only its service. The guard can defer frequent automatic rollouts and skip an unchanged, healthy stack, while explicit per-component commands run right away and update only that component's stamp record. See Justfile, docker/Justfile, and docker/bin/deploy-plan. A first upgrade from an older image has an explicit compatibility path and should follow the repository deployment guidance.

Deploy reviewed master changes over SSH

The production app stack runs on deploy-user@192.168.1.113 under OrbStack in /Users/deploy-user/git/newznab-tmux, with the external MariaDB database on deploy-user@192.168.1.111. Send the deployment owner the merged pull request URL, commit, and validation results. Only that owner builds or deploys production. This procedure describes the existing installation, not initial provisioning.

  1. Connect to deploy-user@192.168.1.113 and verify the fork remote. Fetch xbmc4lyfe/newznab-tmux:master, preserve local changes, and integrate the reviewed revision. If a fast-forward fails, stop and reconcile the checkout without resetting it. Record the full candidate commit and freeze source and configuration for the operation.
  2. Verify the OrbStack context and dependency health, including the external database on 192.168.1.111. Reuse the persistent runtime configuration and data in /Users/deploy-user/git/newznab-tmux/docker, where docker/.env sets COMPOSE_FILE (including /Users/deploy-user/.config/nntmux-db/compose.cutover.yml) and DEPLOY_BY. Don't overwrite configuration or regenerate secrets.
  3. Compare all tracked bind-mounted configuration with the candidate: Caddy, Redis, Manticore, Prometheus, and Grafana. Reconcile differences before deployment.
  4. Run just deploy-plan to inspect the planned actions, then run just deploy (or a single-line component command such as just deploy web or just deploy indexer). It builds while the previous app runs, drains admitted work on affected writers, migrates with app writers stopped when required, recreates only the affected services, and waits for health. Keep database, Redis, and search running.
  5. Verify the deployed commit, image, stamp, service health, intended admission state, and fresh release/NZB evidence before reporting completion.
ssh deploy-user@192.168.1.113
cd /Users/deploy-user/git/newznab-tmux
git fetch origin master
git merge --ff-only origin/master
just deploy-plan
just deploy

Because the checkout and persistent runtime share /Users/deploy-user/git/newznab-tmux and docker/.env defines COMPOSE_FILE and DEPLOY_BY, every routine and component rollout is a single short command. Preserve the shared guard in docker/.deploy.lock rather than creating another lock in a separate checkout. Keep private environment files out of commits and image layers.

A guard refusal, failed drain, unavailable dependency, or recovery hold stops the rollout. Coordinate repair with the owner before another attempt. Don't remove a live lock, stop finite workers forcibly, run Compose down, initialize an existing database, or use FORCE=1 to bypass a failure. Routine deployments can be deferred by the 900-second healthy-rollout interval, and an unchanged healthy stack is skipped. Polls must still invoke guarded deployment when a deferred candidate is pending. The first transition from an old image without cooperative drain has separate maintenance requirements in the reviewed operator guide.

Verify fresh releases and valid NZBs

After the owner reports a healthy rollout, use one coordinated read-only observation window. Confirm the frozen commit from the head= field of the matching deploy … result=finished rc=0 line in .deploy.log, check that each of web, Horizon, scheduler, and indexer runs the image ID of its own role tag (nntmux/<role>:local), optionally compare the stamp's first line with docker/bin/deploy-plan --fingerprint run in the deploy environment, and verify health, database access, and restored admission. Preserve any intentional operator pause. Neither a successful build nor healthy old containers proves that the candidate was deployed.

  1. Record the rollout's healthy completion time and a committed release-ID baseline. Use a bounded indexed query against the actual deployed schema. Retain the query limit, timestamps, and result count. Wait for natural processing rather than starting jobs for the demonstration.
  2. Find a newly persisted release after the rollout and correlate its identifier with its NZB. Record the release state, file size, modification time, and digest. Check that the file was created after the rollout, rather than reusing a preexisting artifact.
  3. Decode gzip and parse the NZB XML within explicit byte and work limits. Record file and segment counts. Valid gzip alone doesn't prove a valid NZB, and syntax validity doesn't prove provider availability or successful payload verification.
  4. Retain the source/image identity and evidence timestamps with the result. A completed assessment cycle, collection deletion, or an unchanged queue isn't proof of a newly published release. If no eligible input arrives, report the missing fresh-publication proof and continue coordinated observation.

When the scheduler or indexer holds active finite verification or indexing jobs, cooperative drain waits for those jobs to finish before stopping the container (for example 298 seconds on eb73b4ae0 and 365 seconds on 739fefa62). Polling and the 15-minute automatic batching interval can also add latency before an automatic rollout starts, whereas explicit single-component commands (just deploy web, just deploy indexer) run right away without waiting for the batching interval. Retain Docker's layer cache and nntmux/base:local for routine updates. Detailed ongoing deployment telemetry belongs in Grafana once implemented and verified.

Inspect the installation

just docker ps
just docker logs s=indexer
just docker tmux
just docker help

Detach from tmux with Ctrl-a, then d. Persistent data lives in docker/data/, logs in docker/logs/, and database backups in docker/backups/. If initialization fails, inspect logs before retrying. Don't reset a partially initialized database as a troubleshooting shortcut.

For an initialized stack, just docker up uses the guarded path. Use just deploy for updates. Repeating init reapplies starter groups and tuning. Avoid a routine Compose shutdown during app upgrades so database, Redis, and search can remain available.

Hosted deployment runbooks

The repository also contains Docker deployment paths for Amazon Web Services (AWS), Hetzner, and OVHcloud. Hosted deployment uses provider-specific Terraform roots and release commands. Hetzner and OVHcloud examples require Vault-backed app settings and encrypted backup configuration. Those paths have provider-specific account, network, storage, and recovery prerequisites. They're not required for the local Compose quick start. Begin with the cloud Docker runbooks.

The historical fork snapshot includes native physical-server tooling. A later cleanup removed that unused tooling. Use the Docker deployment paths for the current checkout.
