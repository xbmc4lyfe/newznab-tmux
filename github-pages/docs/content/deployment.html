Run the experimental fork locally

The supported quick start in this snapshot is a local Docker Compose stack. Hosted and physical-server deployment runbooks are separate options for existing operators.

Plan for a substantial workload. The site uses 32–64 GB RAM as a planning target for the intended personal setup. This is a recommendation, not a measured minimum, capacity test, or throughput promise. The README's supplied Compose limits total roughly 30 GiB and its MariaDB configuration sets an 8 GiB buffer pool. Adjust those settings to your host before starting.

Requirements

The fork README lists Git, Make, Python 3, Docker with Compose v2, and Usenet provider credentials. On macOS it names Docker Desktop or OrbStack. On Linux, Docker Engine with the Compose plugin. The supplied setup also needs adequate disk for the database, NZB storage, and verification scratch. Its example allows up to 200 GiB for verification scratch while keeping 10 GiB free. This scratch allowance is separate from the space needed for persistent data. Review the machine-readable defaults before allocating a host. See the README requirements.

Clone the fork

git clone https://github.com/xbmc4lyfe/newznab-tmux.git
cd newznab-tmux

Configure a provider

  1. Clone the fork and enter the checkout.
  2. Create docker/config/usenet_servers.json with provider host, port, transport encryption setting, username, password, and connection count. Keep this ignored local file private and restrict its permissions.
  3. Set NNTP_PRIMARY_HOST and NNTP_ALT_HOST, then run make -C docker env. Set the alternate host to a separate provider only when you have configured one.
  4. Review generated docker/.env and docker/config/app.env. These contain secrets, generated app and database passwords, memory limits, and optional metadata keys.

Create docker/config/usenet_servers.json in your editor with your own provider values:

{
  "usenet_servers": [
    {
      "host": "news.example.com",
      "port": 563,
      "ssl": true,
      "username": "YOUR_USERNAME",
      "password": "YOUR_PASSWORD",
      "connections": 10
    }
  ]
}
chmod 600 docker/config/usenet_servers.json
export NNTP_PRIMARY_HOST=news.example.com
export NNTP_ALT_HOST="$NNTP_PRIMARY_HOST"
make -C docker env

Replace the sample host and credentials before running the commands. If you use a separate fallback provider, add its server object and set NNTP_ALT_HOST to that server's host. The generated docker/.env and docker/config/app.env contain secrets. Keep them private. Review ports, Docker VM memory limits, and app settings before initialization. This example follows the frozen provider setup section. The Compose stack uses bind-mounted persistent state under docker/data/.

Review processing settings first

Seeded defaults enable starter groups and configure 12 header workers, 30 backfill workers, 16 additional-processing workers, and 4 information-file workers. The README warns that the JSON connection count doesn't reduce those worker counts. Lower the database seed values to fit your provider's connection allowance, hardware, and terms before initialization. Initialization starts indexing automatically. See the README's tuning warning.

Initialize a fresh installation

make -C docker init DEPLOY_BY=local-setup
make -C docker ps

This builds the images, initializes MariaDB and search tables, installs monitoring, seeds groups and tuning, attempts a PreDB import, and starts the stack. Open http://localhost:8080. Find the generated administrator password in docker/config/app.env. Read it locally with rg '^ADMIN_PASS=' docker/config/app.env. The initializer skips installation when the persistent install lock already exists. Read the first-run notes before retrying a partial install.

Update an initialized local stack

Back up MariaDB and separately preserve configuration, NZB/storage files, and other state you need for recovery. The database backup target doesn't cover those files. Update the checkout only after preserving local changes, then use the guarded deployment:

make -C docker backup
# Update your checkout to the reviewed revision before deploying.
make -C docker deploy DEPLOY_BY=local-update

The Make target serializes deployments, builds while services are live, drains scheduler and indexer work, waits for Horizon, stops app writers, runs migrations, then starts the app services and waits for their health checks. Persistent database, Redis, and search services remain running during a routine app update. The guard can defer frequent rollouts and skip an unchanged, healthy stack. See the Make targets and the deployment sequence. A first upgrade from an older image has an explicit compatibility path and should follow the repository deployment guidance.

Inspect the installation

make -C docker ps
make -C docker logs s=indexer
make -C docker tmux
make -C docker help

Detach from tmux with Ctrl-a, then d. Persistent data lives in docker/data/, logs in docker/logs/, and database backups in docker/backups/. If initialization fails, inspect logs before retrying. Don't reset a partially initialized database as a troubleshooting shortcut.

For an initialized stack, make -C docker up DEPLOY_BY=local-start uses the guarded path. Use deploy for updates. Repeating init reapplies starter groups and tuning. Avoid a routine Compose shutdown during app upgrades so database, Redis, and search can remain available.

Hosted and bare-metal runbooks

The repository also contains deployment paths for Amazon Web Services (AWS), Hetzner, OVHcloud, and physical servers. Hosted deployment uses provider-specific Terraform roots and release commands. Hetzner and OVHcloud examples require Vault-backed app settings and encrypted backup configuration. Those paths have provider-specific account, network, storage, and recovery prerequisites. They're not required for the local Compose quick start. Begin with the cloud and bare-metal runbooks.
