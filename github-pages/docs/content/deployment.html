Run the experimental fork locally

The supported quick start in this snapshot is a local Docker Compose stack. Hosted Docker deployment runbooks are separate options for existing operators.

Plan for a substantial workload. The site uses 32–64 GB RAM as a planning target for the intended personal setup. This is a recommendation, not a measured minimum, capacity test, or throughput promise. The README's supplied Compose limits total roughly 30 GiB and its MariaDB configuration sets an 8 GiB buffer pool. Adjust those settings to your host before starting.

Requirements

The fork README lists Git, Make, Python 3, Docker with Compose v2, and Usenet provider credentials. On macOS it names Docker Desktop or OrbStack. On Linux, Docker Engine with the Compose plugin. The supplied setup also needs adequate disk for the database, NZB storage, and verification scratch. Its example allows up to 200 GiB for verification scratch while keeping 10 GiB free. This scratch allowance is separate from the space needed for persistent data. Review the machine-readable defaults before allocating a host. See the README requirements.

Clone the fork

git clone https://github.com/xbmc4lyfe/newznab-tmux.git
cd newznab-tmux

Configure a provider

  1. Clone the fork and enter the checkout.
  2. Create docker/config/usenet_servers.json with provider host, port, transport encryption setting, username, password, and connection count. Keep this ignored local file private and restrict its permissions.
  3. Set NNTP_PRIMARY_HOST and NNTP_ALT_HOST, then run just --justfile docker/Justfile env. Set the alternate host to a separate provider only when you have configured one.
  4. Review generated docker/.env and docker/config/app.env. These contain secrets, generated app and database passwords, memory limits, and optional metadata keys.

Create docker/config/usenet_servers.json in your editor with your own provider values:

{
  "usenet_servers": [
    {
      "host": "news.example.com",
      "port": 563,
      "ssl": true,
      "username": "YOUR_USERNAME",
      "password": "YOUR_PASSWORD",
      "connections": 10
    }
  ]
}
chmod 600 docker/config/usenet_servers.json
export NNTP_PRIMARY_HOST=news.example.com
export NNTP_ALT_HOST="$NNTP_PRIMARY_HOST"
just --justfile docker/Justfile env

Replace the sample host and credentials before running the commands. If you use a separate fallback provider, add its server object and set NNTP_ALT_HOST to that server's host. The generated docker/.env and docker/config/app.env contain secrets. Keep them private. Review ports, Docker VM memory limits, and app settings before initialization. The commands follow the current docker/Justfile; the provider setup was originally recorded in this earlier README revision. The Compose stack uses bind-mounted persistent state under docker/data/.

Review processing settings first

Seeded defaults enable starter groups and configure 12 header workers, 30 backfill workers, 16 additional-processing workers, and 4 information-file workers. The README warns that the JSON connection count doesn't reduce those worker counts. Lower the database seed values to fit your provider's connection allowance, hardware, and terms before initialization. Initialization starts indexing automatically. See the README's tuning warning.

Initialize a fresh installation

just --justfile docker/Justfile init DEPLOY_BY=local-setup
just --justfile docker/Justfile ps

This builds the images, initializes MariaDB and search tables, installs monitoring, seeds groups and tuning, attempts a PreDB import, and starts the stack. Open http://localhost:8080. Find the generated administrator password in docker/config/app.env. Read it locally with rg '^ADMIN_PASS=' docker/config/app.env. The initializer skips installation when the persistent install lock already exists. Read the first-run notes before retrying a partial install.

Update an initialized local stack

Back up MariaDB and separately preserve configuration, NZB/storage files, and other state you need for recovery. The database backup target doesn't cover those files. Update the checkout only after preserving local changes, then use the guarded deployment:

just --justfile docker/Justfile backup
# Update your checkout to the reviewed revision before deploying.
just --justfile docker/Justfile deploy DEPLOY_BY=local-update

The deploy recipe serializes deployments and builds while services are live. Commits that cannot change an image (documentation, tests, files outside the Docker build context) are skipped. Otherwise it rebuilds only the affected role images and recreates only those app services: a change confined to one role (for example Vite assets for web) leaves the other writers running. For a shared PHP or configuration change it stops Horizon first, so its active jobs finish while the scheduler and indexer keep queueing work, then drains the scheduler and indexer and recreates the four app services after health checks. Every app writer is stopped before migrations, which run when a migration changed, when a Compose change reaches all four app services (for example a database cutover or an edit to the mounted docker/config/app.env), or when an otherwise unexplained Compose change requires it. A changed stateful data service stops every writer before it is recreated; a changed mounted configuration file recreates only its service. The guard can defer frequent rollouts and skip an unchanged, healthy stack. See docker/Justfile and docker/bin/deploy-plan. A first upgrade from an older image has an explicit compatibility path and should follow the repository deployment guidance.

Deploy reviewed master changes over SSH

The production deployment owner is DEPLOY M5STEPHEN. Send that chat the merged pull request URL, commit, and validation results. Only that owner builds or deploys production. The current installation builds on the SSH host's OrbStack engine; the development machine's Docker engine is a different target. This procedure describes the existing installation, not initial provisioning.

  1. Connect to the deployment host and verify the fork remote. Fetch xbmc4lyfe/newznab-tmux:master, preserve local changes, and integrate the reviewed revision. If a fast-forward fails, stop and reconcile the checkout without resetting it. Record the full candidate commit and freeze source and configuration for the operation.
  2. Verify the OrbStack context and dependency health, including the external database. Reuse the persistent runtime configuration and data. Confirm that the candidate's ignored docker/.env and docker/config/app.env links resolve to their corresponding runtime files. Don't overwrite configuration or regenerate secrets. Check that Make's app image and timeouts match the effective Compose configuration.
  3. Compare all tracked bind-mounted configuration with the candidate: Caddy, Redis, Manticore, Prometheus, and Grafana. Reconcile differences before deployment. A proxy, data-service or monitoring configuration change needs its own owned update plan; an app rollout doesn't reload those services.
  4. Run the guarded target below with the same ordered Compose files, project directory, source identity and persistent guard/history paths. It builds while the previous app runs, drains admitted work, migrates with app writers stopped, recreates the four app services, and waits for health. Keep database, Redis, and search running.
  5. Verify the deployed commit, image, stamp, service health, intended admission state and fresh release/NZB evidence before reporting completion.
ssh air@192.168.1.111
export PATH="/opt/homebrew/bin:/opt/homebrew/sbin:$PATH"
export DOCKER_CONTEXT=orbstack
cd /Users/air/git.xbmc4lyfe
git remote get-url origin
git fetch origin master
# Preserve local changes and resolve any divergence before proceeding.
git merge --ff-only origin/master
git rev-parse HEAD
docker context inspect orbstack
# Verify the socket is /Users/air/.orbstack/run/docker.sock.
# Complete the configuration and dependency checks above before deploying.
export COMPOSE_FILE="/Users/air/git.xbmc4lyfe/docker/docker-compose.yml:/Users/air/.config/nntmux-db/compose.cutover.yml"
just --justfile docker/Justfile deploy DEPLOY_BY="DEPLOY M5STEPHEN" \
  DC='docker compose --project-directory /Users/air/git/newznab-tmux/docker' \
  DEPLOY_REPO=/Users/air/git.xbmc4lyfe \
  DEPLOY_LOCK_DIR=/Users/air/git/newznab-tmux/docker/.deploy.lock \
  DEPLOY_LOG=/Users/air/git/newznab-tmux/docker/.deploy.log \
  DEPLOY_STAMP=/Users/air/git/newznab-tmux/docker/.deploy.stamp \
  DEPLOY_SUCCESS_TIME=/Users/air/git/newznab-tmux/docker/.deploy.time

Pass DC as a trailing argument or exported variable; it reaches every nested helper. The nested build uses the candidate's docker/.build.stamp; healthy rollout history belongs to the persistent runtime. Preserve this shared guard rather than creating another lock in a new checkout. Keep private environment files out of commits and image layers.

A guard refusal, failed drain, unavailable dependency, or recovery hold stops the rollout. Coordinate repair with the owner before another attempt. Don't remove a live lock, stop finite workers forcibly, run Compose down, initialize an existing database, or use FORCE=1 to bypass a failure. Routine deployments can be deferred by the 900-second healthy-rollout interval, and an unchanged healthy stack is skipped. Polls must still invoke guarded deployment when a deferred candidate is pending. The first transition from an old image without cooperative drain has separate maintenance requirements in the reviewed operator guide.

Verify fresh releases and valid NZBs

After the owner reports a healthy rollout, use one coordinated read-only observation window. Confirm the frozen commit from the head= field of the matching deploy … result=finished rc=0 line in .deploy.log, check that each of web, Horizon, scheduler and indexer runs the image ID of its own role tag (nntmux/<role>:local), optionally compare the stamp's first line with docker/bin/deploy-plan --fingerprint run in the deploy environment, and verify health, database access, and restored admission. Preserve any intentional operator pause. Neither a successful build nor healthy old containers proves that the candidate was deployed.

  1. Record the rollout's healthy completion time and a committed release-ID baseline. Use a bounded indexed query against the actual deployed schema; retain the query limit, timestamps, and result count. Wait for natural processing rather than starting jobs for the demonstration.
  2. Find a newly persisted release after the rollout and correlate its identifier with its NZB. Record the release state, file size, modification time, and digest. Check that the file was created after the rollout, rather than reusing a preexisting artifact.
  3. Decode gzip and parse the NZB XML within explicit byte and work limits. Record file and segment counts. Valid gzip alone doesn't prove a valid NZB; syntax validity doesn't prove provider availability or successful payload verification.
  4. Retain the source/image identity and evidence timestamps with the result. A completed assessment cycle, collection deletion or an unchanged queue isn't proof of a newly published release. If no eligible input arrives, report the missing fresh-publication proof and continue coordinated observation.

Inspect the installation

just --justfile docker/Justfile ps
just --justfile docker/Justfile logs s=indexer
just --justfile docker/Justfile tmux
just --justfile docker/Justfile help

Detach from tmux with Ctrl-a, then d. Persistent data lives in docker/data/, logs in docker/logs/, and database backups in docker/backups/. If initialization fails, inspect logs before retrying. Don't reset a partially initialized database as a troubleshooting shortcut.

For an initialized stack, just --justfile docker/Justfile up DEPLOY_BY=local-start uses the guarded path. Use deploy for updates. Repeating init reapplies starter groups and tuning. Avoid a routine Compose shutdown during app upgrades so database, Redis, and search can remain available.

Hosted deployment runbooks

The repository also contains Docker deployment paths for Amazon Web Services (AWS), Hetzner, and OVHcloud. Hosted deployment uses provider-specific Terraform roots and release commands. Hetzner and OVHcloud examples require Vault-backed app settings and encrypted backup configuration. Those paths have provider-specific account, network, storage, and recovery prerequisites. They're not required for the local Compose quick start. Begin with the cloud Docker runbooks.

The historical fork snapshot includes native physical-server tooling. A later cleanup removed that unused tooling. Use the Docker deployment paths for the current checkout.
