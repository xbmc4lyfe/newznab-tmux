These model rules apply to Codex subagents only; Claude uses `CLAUDE.md`. Keep the human-selected main-session model unchanged. Delegate bounded independent work when useful; do small coupled work directly.

| Delegated task | Model | Effort |
| --- | --- | --- |
| File/symbol inventory, source lookup, log summarization, mechanical edits | `gpt-6-luna` | `high` |
| Bounded Laravel implementation or focused correctness review | `gpt-6.1-sol` | `medium` |
| Cross-service debugging, transaction reasoning, concurrency fixes | `gpt-6.1-sol` | `high` |

- Choose complexity by uncertainty, interacting state, and failure impact; a short diff can require the strongest route.
- Set both `model` and `reasoning_effort` explicitly on native `spawn_agent`; use `fork_turns="none"` with a self-contained brief when overrides require it. Command-line children use `--model` and `-c model_reasoning_effort=...`.
- Include goal, relevant paths/skills, constraints, file ownership, validation, and completion evidence. Give independent reviewers the contract and diff without the implementer's conclusions.
- Escalate when evidence shows the task exceeds its route; give a concrete reason. Reserve `xhigh`/`max` for unresolved difficult reasoning. Check advertised model/effort support; report unavailable overrides rather than silently inheriting or bypassing permissions.
- Parallelize independent reads; give each writer exclusive files or an isolated worktree. Keep the source/experiment/deployment ownership rules below.

# Git workflow and code review

A human prompt or goal authorizes agents to commit task changes, push a feature branch, open a PR, and squash-merge it into `master` in `xbmc4lyfe/newznab-tmux` after all review gates pass. Follow [.ai/rules/git-workflow.md](.ai/rules/git-workflow.md). This permission doesn't authorize deployment, production changes, or dependency changes.

- Before opening a PR, obtain an independent local review with no findings using Antigravity (via an independent subagent) or Codex (via a Codex subagent or separate command-line process).
- After opening the PR, obtain a PR review from Antigravity or request `@codex review`. Address and reply to every finding, resolve each review thread, and obtain another review after fixes or an explanation that a finding doesn't apply.
- Merge only after the reviewer (Antigravity or Codex) gives an explicit approval or go-ahead for the current PR head and required checks pass. Every change after a review requires a fresh review with no findings.
- If using the GitHub Codex app and it reports exhausted review credits, use a fresh independent local review of the current PR head via Antigravity or Codex (`gpt-6.1-sol` or a stronger model, `high` effort, and normal speed). Record the review and commit hash in the PR.
- Feature pull requests target this fork's `master`. Upstream synchronization with `NNTmux/newznab-tmux` uses a merge commit and requires a separate synchronization request.

## Code review rules

- Review the complete PR diff against its destination branch. Report every actionable finding and identify the reviewed head commit hash. An exit code alone isn't approval.
- Check the review gates, macOS/Linux platform policy, and [Rust performance requirements](.ai/rules/rust-performance.md) when they apply. Approve only after the current revision has no unresolved findings.

## Before planning or editing

- Start every new implementation, fix, or feature in an isolated Git worktree on a new branch that does not already exist on the remote. Use the `codex/` prefix and verify the name against remote branches before creating it; never perform new development on a shared checkout or `master`.
- Fetch the latest `master` from `xbmc4lyfe/newznab-tmux` before creating that worktree/branch, and base it on the fetched commit. Verify the remote URL: this is the fork's `master`, not `NNTmux/newznab-tmux/master`. Reuse the worktree and branch already created for the current task; continuing an explicitly requested existing PR keeps that PR's branch.
- While actively working, fetch and integrate newer commits from `xbmc4lyfe/newznab-tmux/master` every 30–60 minutes. Refresh at the beginning of each resumed work session if the last fetch is older than 30 minutes. Preserve unrelated and uncommitted work; never reset or discard it to synchronize.
- After a PR is merged, fetch the fork's `master` again before creating the next task's worktree and new `codex/` branch. Base that branch on the newly fetched commit rather than the previous task branch or a stale local `master`.
- Fetch and integrate any newer commits from `xbmc4lyfe/newznab-tmux/master` again immediately before the first local review and again before creating the PR. Resolve conflicts, retain the intended behavior, and rerun affected checks before review/submission; do not review or submit a stale base just because the branch was current when work began. If `master` has not advanced, no additional merge is needed.
- Read [.ai/rules/index.md](.ai/rules/index.md), every rule matching the target paths, and search `.ai/rules` for task keywords.
- Record durable shared rules with Boost's `record-rule`; don't substitute personal memory.
- Follow existing sibling conventions and reuse existing components. Keep dependencies and new base directories subject to user approval.
- Create documentation only when requested. Keep replies concise.

## Rust implementation and performance

Try Rust first for new app logic. When fixing or upgrading code in another language, attempt a Rust replacement for the affected logic. Compare it with the existing implementation or an implementation native to that codebase. Adopt Rust only after correctness checks and reproducible benchmarks show at least a 1.5× speedup on common paths and uncommon p99 workloads; aim for 2–3×. Include integration overhead. If Rust doesn't meet the threshold, retain the native implementation and document the evidence. Follow [.ai/rules/rust-performance.md](.ai/rules/rust-performance.md).

## Shared runtime

- Feature sessions don't deploy or restart the shared stack. The deployment owner uses `just --justfile docker/Justfile deploy DEPLOY_BY=<session name>` and the deploy guard.
- To inspect which services would build or redeploy without executing changes, use `just --justfile docker/Justfile deploy-plan` (or `DRY_RUN=1 just --justfile docker/Justfile deploy DEPLOY_BY=<session name>`). To prepare images while services remain live, use `just --justfile docker/Justfile build DEPLOY_BY=<session name>`. To rebuild and recreate all four app services immediately (with migrations) through the same drain checks; data and infra services are recreated only when their inputs changed, use `just --justfile docker/Justfile deploy DEPLOY_BY=<session name> FORCE=1`. Routine code redeployments use `deploy` without `FORCE`; keep database, Redis and search containers running unless their effective inputs changed, instead of using Compose `down`.
- Frequent redeploy polls (for example every four minutes) coalesce changes with `DEPLOY_MIN_INTERVAL=900`, measured from the last healthy deployment. With pending changes and healthy services, the next attempt becomes eligible after 15 minutes and starts on a subsequent poll; polling, builds and drains add latency. `FORCE=1` bypasses batching and unchanged checks, but retains the guard, drains, migrations and health checks. An unchanged, healthy stack (including commits that only modify documentation, `.ai/`, or tests) skips the entire rollout. Invoke guarded `deploy` on every poll, including polls with no newly fetched commit: a deferred build is still pending, and `.deploy.stamp` records per-service content fingerprints from the last healthy rollout rather than the checkout's latest commit.
- Export `COMPOSE_FILE` as an absolute colon-separated list when the stack uses overrides (including database cutovers). The same effective Compose configuration is hashed per service and used for preflight, drain, migration and startup; keep every deployment call on that exact file list. Existing `DC` argv overrides are shared by all helpers and parsed as arguments without evaluating shell code.
- `just --justfile docker/Justfile up` also routes existing app containers through the guarded deploy (including stopped containers after a failed migration); a stack with no app containers retains initial bringup.
- The first upgrade from an image without `tmux:drain` requires an authorized maintenance window and `DEPLOY_LEGACY_DRAIN=1 just --justfile docker/Justfile deploy DEPLOY_BY=<session name>` (optionally `DEPLOY_LEGACY_DRAIN_TIMEOUT=3600`, default 1800 seconds). The streamed compatibility helper pauses dispatch, waits for the old monitor and finite workers to exit naturally, and restores prior runtime flags and the monitor on timeout or pre-stop failure. Unknown active panes and interactive consoles block the upgrade; close idle consoles only after checking they have no active jobs. Timeouts identify blocking roles without logging command arguments. Legacy IRC alone disconnects at final container stop; messages in flight have no replay guarantee during this one-time transition. No finite worker is force-killed by the bridge.
- During that first upgrade, the old scheduler is also frozen before waiting for its detached background workers. The helper requires Docker init, Linux pidfd support, Python 3.9+, and a readable dedicated cgroup PID counter; it fails closed if ownership cannot be verified. Once every finite scheduler worker has exited, Docker stops that frozen coordinator with a one-second timeout; only the idle coordinator can require forced termination, and it cannot admit another job during cutover. On an aborted drain, the helper restores its original running/stopped state. Subsequent images use cooperative drain. Without the explicit opt-in, old running images fail closed.
- If an interrupted first-upgrade attempt leaves a legacy scheduler barrier owned by an earlier operation, the deployment owner must first inspect the saved journal and verify authorization to recover that operation. Set `SCHEDULER_RECOVERY_TOKEN` to its exact recorded owning token, then restore under the same guard: `DEPLOY_BY=<owner> docker/bin/deploy-guard run resume-scheduler -- docker/bin/compose exec -T scheduler python3 - resume 0 "$SCHEDULER_RECOVERY_TOKEN" < docker/bin/legacy-scheduler-drain.py`. A tokenless resume deliberately leaves token-owned barriers intact. Preserve `COMPOSE_FILE` overrides, verify invocation source pins and exclusive signal authority, and inspect identity/restoration failures before retrying deployment. Old, intent-only or foreign-protocol journals remain unconfirmed and require investigation with the coordinator held; never edit or clear the journal, or signal a replacement PID, to bypass ownership and confirmation checks.
- Builds use the root Dockerfile's cached `base` target (`BASE_IMAGE`, default `nntmux/base:local`) and thin per-service targets (`selfhosted-web`, `selfhosted-horizon`, `selfhosted-scheduler`, `selfhosted-indexer`, plus `selfhosted` for all-in-one compatibility): system packages, PHP extensions, native libraries and locked dependencies are cached before application source. `.build.stamp` records per-service build fingerprints; `.deploy.stamp` and `.deploy.time` record only healthy rollouts.
- Compose sends explicit `SIGTERM` through its init process; the indexer trap drains for `INDEXER_DRAIN_TIMEOUT=90` seconds within its 120-second stop grace. Horizon has 1920 seconds of stop grace to cover its 1860-second fingerprint supervisor timeout. The scheduler uses a Linux child-subreaper supervisor so detached background jobs remain owned and finish before container exit; its stop grace is also 1920 seconds. Deployment drains admitted work while web stays up, so active long jobs can delay rollout.
- Scheduler preflight uses `DEPLOY_SCHEDULER_DRAIN_TIMEOUT=1800` seconds; tune it through the deployment environment or `docker/.env`. In a current scheduler container, `python3 /app/docker/app/bin/scheduler.py drain --timeout=1800` pauses admission and waits for all owned background work. `restore` restores the state before that drain (used on deployment failure); `resume` explicitly reopens admission; `status` reports state and `check` verifies quiescence. The deployment helper pairs drain/restore with a unique operation token so recovery cannot undo an unrelated operator pause. A timeout or interrupted pending drain restores admission without killing finite jobs.
- Deployment builds only changed images while the old stack runs, probes the drain capabilities of the writers it will touch, stops Horizon first when it is affected (its active jobs finish while the scheduler and indexer keep queueing work), then drains the affected scheduler and indexer (`tmux:drain --timeout=900`, `DEPLOY_DRAIN_TIMEOUT`) — or every writer when migrations or stateful data services change — holds remote verification workers out with the new image's `releases:verification-barrier` when every writer stops (`DEPLOY_REMOTE_DRAIN_TIMEOUT`, default 900 seconds), stops only the drained/affected writers, runs migrations when required, then recreates only affected services and waits for health. Drain failure aborts before stopping writers/migrating and restarts Horizon; never bypass drain or stop unaffected data services. After a migration/health failure, repair under the same deployment ownership and retry; no automatic schema rollback. A barrier still running after a failed attempt keeps remote workers held; the next healthy rollout adopts and releases it. Any failed run that held a barrier records an owed release (`.deploy.stamp.barrier-owed`), so the next run, even a no-op or selective one, takes a barrier and clears the durable pause without repeating a completed migration; a recreated data service is followed by a fresh barrier before migration.
- Native and legacy indexer drains serialize control commands and pair deployment drain/resume with the same operation token. Abort recovery only releases a pause created by that deployment; an earlier operator pause remains intact. Direct operator `tmux:drain --resume` without a token retains explicit manual recovery semantics.
- Aborted drains restore the previous runtime flags and restart a previously live monitor after it exits. Recovery allows another 15 seconds for the monitor to exit naturally; if it remains stuck, report the restoration failure and keep scheduling paused. Investigate the monitor before retrying `php artisan tmux:drain --resume --session=nntmux` inside the indexer, or retry the opted-in guarded deployment for a legacy image. Never force-kill finite workers to bypass a failed drain.
- Treat production monitoring as read-only unless the user authorizes a specific operational change. Don't launch jobs, change NNTP/concurrency settings, restart, or deploy while observing.

### Master rollout procedure and evidence

- The deployment owner identifies the live runtime and exact Compose file list from the running container labels, fetches `xbmc4lyfe/newznab-tmux:master`, and integrates it into the candidate checkout without discarding local changes. Freeze the candidate source and effective configuration before the guarded rollout; a newer commit can wait for the next poll. A fetch, checkout update or image build alone does not deploy production.
- On each authorized poll, run `just --justfile docker/Justfile deploy DEPLOY_BY=<session name>` from the candidate checkout with the runtime's approved absolute `COMPOSE_FILE` list, Compose project directory and shared guard/history paths. Retain the single owner and guard. Report a guard refusal, failed drain or recovery hold to the owner; do not repeatedly retry an unresolved failure or use `FORCE=1` to work around it. The one-time legacy transition above remains a separate readiness gate for running legacy images before routine cooperative rollouts are available.
- Measure change-to-healthy latency separately from attempt duration. Attempt duration is the outer `deploy result=started` to its matching `deploy result=finished` in `docker/.deploy.log`, including build and drain time. Report build, drain, migration and health timing separately when captured; do not infer missing phase timings. Cached builds reduce build time, while active finite jobs can still delay or abort a rollout. Claim a fast rollout only from measured end-to-end evidence.
- For a trailing-window report, state the cutoff and timezone, list each attempt's start, finish, candidate commit, duration and outcome, and identify attempts crossing the window boundary or still running. Count completed deployments separately from failed attempts, skipped/deferred polls and nested `build`/`up` entries. An exit-zero skip or defer is not a completed rollout, and neither is a `finished rc=0 (no service affected; stamped without a rollout)` attempt, which closes its `started` line without rolling anything out.
- Before reporting success, verify the deployment stamp, running image/source identity, all four app services' health, restored admission consistent with prior operator pauses, and resumed processing/progress. Use `.deploy.log` as the available deployment-history source; detailed Grafana reporting requires separately implemented and verified telemetry before it can supply evidence. A passing review, build or healthy old stack does not establish that the candidate was deployed, that backfill progress was preserved, or that the rollout was issue-free.
