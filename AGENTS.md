- If using the GitHub Codex app and it reports exhausted review credits, use a fresh independent local review of the current PR head via Antigravity or Codex (`gpt-6.1-sol` or a stronger model, `high` effort, and normal speed), or substitute a subagent within whatever harness you are using if local Codex does not work. Record the review and commit hash in the PR.

## Shared runtime

- Feature sessions don't deploy or restart the shared stack. The deployment owner uses `just deploy` (with `DEPLOY_BY=<session name>` set in `docker/.env`, exported, or passed on the command line) and the deploy guard. By default (`DEPLOY_SYNC_REMOTE=auto`, `DEPLOY_GIT_REMOTE=origin`, `DEPLOY_GIT_BRANCH=master`), `just deploy-plan`, `just build-stack`, and `just deploy` verify that the checkout is on the default branch, fetch `origin/master` from GitHub, and fast-forward the checkout before fingerprinting or building, failing closed if the checkout is on another branch, has unpushed or diverged local commits, or cannot reach the remote (`DEPLOY_SYNC_REMOTE=0` disables remote sync for explicit offline testing).
- To inspect which services would build or redeploy without executing changes, use `just deploy-plan` (or `just deploy-plan <component>`, or `DRY_RUN=1 just deploy`). To deploy or recreate specific components (`web`, `horizon`, `scheduler`, `indexer`, `proxy`, `monitoring`, `redis`, `manticore`, `mariadb`, `mailpit`, `grafana`, `prometheus`), use `just deploy <component>` or `just deploy-<component>` (`DEPLOY_TARGETS=<component>`); explicit component targets bypass the batching cooldown and redeploy the requested component even when it is already stamped as unchanged in `.deploy.stamp`. To prepare images while services remain live, use `just build-stack` (or `just build-stack <component>`). To rebuild and recreate all four app services immediately (with migrations) through the same drain checks; data and infra services are recreated only when their inputs changed, use `just deploy FORCE=1`. Routine code redeployments use `just deploy` without `FORCE`; keep database, Redis and search containers running unless their effective inputs changed, instead of using Compose `down`.
- Frequent redeploy polls (for example every four minutes) coalesce changes with `DEPLOY_MIN_INTERVAL=900`, measured from the last healthy deployment. With pending changes and healthy services, the next attempt becomes eligible after 15 minutes and starts on a subsequent poll; polling, builds and drains add latency. `FORCE=1` bypasses batching and unchanged checks, but retains the guard, drains, migrations and health checks. An unchanged, healthy stack (including commits that only modify documentation, `.ai/`, or tests) skips the entire rollout. Invoke guarded `deploy` on every poll, including polls with no newly fetched commit: a deferred build is still pending, and `.deploy.stamp` records per-service content fingerprints from the last healthy rollout rather than the checkout's latest commit.
- Export `COMPOSE_FILE` as an absolute colon-separated list when the stack uses overrides (including database cutovers). The same effective Compose configuration is hashed per service and used for preflight, drain, migration and startup; keep every deployment call on that exact file list. Existing `DC` argv overrides are shared by all helpers and parsed as arguments without evaluating shell code.
- Each service's fingerprint covers its rendered definition, the contents of its bind-mounted configuration (including directory symlink targets), and the file contents or resolved environment values (never logged) behind the configs and secrets it uses; an unresolvable environment source aborts the plan. Planning fails closed on override services with a `build:` section, `network_mode`/`ipc`/`pid` of the form `service:` or `container:`, `volumes_from` (`pid: host` is fine), `depends_on.<provider>.restart: true`, more than one replica of an app service, an app service with a disabled or removed health check, app services whose `DB_*` connection settings differ, or a data service that depends on an app service (label such an override service `nntmux.deploy.stateless: "true"` if it is stateless); it also fails closed when `DC` passes `--env-file` or `COMPOSE_ENV_FILES` is set. The Justfile and `docker/bin/compose` read `docker/.env` with one shared parser (`docker/bin/compose_dotenv.py`) that, like Compose, decodes compose-go's escapes in double-quoted values (`\\`, `\"`, `\$`, `\a \b \f \n \r \t \v`, octal `\0NNN`; `\$` is a literal `$`), keeps any other backslash sequence, and unescapes `\'` in single-quoted values; it also reads `KEY: value` and `KEY:value` lines and a leading BOM, drops text after a closing quote, and never reads a multi-line value's lines as assignments; `$$` is a literal `$` as written. The stamp records the effective Compose project name and Docker daemon (`DOCKER_HOST` (together with `DOCKER_CONTEXT` when both are set), else `DOCKER_CONTEXT` with its endpoint, else the current context; `DC` may not pass daemon-selecting Docker options, nor a standalone `docker-compose` its `-H`/`--host`/`-c`/`--context` anywhere); a later change to either aborts the plan instead of starting a second stack on the same data. A service the override adds outside the known roster is treated as stateful data (changed only with every writer quiesced; started without a drain only while it has no container and no changed record) unless it carries the label `nntmux.deploy.stateless: "true"`. Data and infrastructure services are applied in one `depends_on` order: infrastructure that needs a changed data service follows it after the drain, and infrastructure whose app provider is not running healthy follows the app rollout. A running data or infrastructure container whose image ID differs from its tag's local image (for example after `docker pull`) is recreated, a data service through the writer drain. Services are applied with `--pull never`, so Compose never pulls a `latest` tag the plan did not inspect. A rendered data or infrastructure service with no container makes the stack not current. A recorded data service that is no longer rendered (renamed onto the same storage) keeps running as an orphan until a data rollout stops it, after the writers are quiesced and before its successor starts; its `orphan:` stamp record survives later no-op stamps until its container stops, so a successor added by a later poll also starts only after the drain and the orphan's stop. A service whose bind source is itself a symlink (anywhere, also outside the project) and that has no per-service record (first deployment, legacy stamp) is recreated rather than reconciled. `app.env` here is the file the app services bind-mount as `/app/.env` (all four must mount the same one; default `docker/config/app.env`). A database connection key in `app.env` (`DB_URL`, `DB_HOST`, `DB_CONNECTION`, `DB_PORT`, `DB_SOCKET`, `DB_DATABASE`) that uses `${...}` interpolation aborts the plan, because the database it selects cannot be determined. A database host (`DB_URL`'s `host=` query option, then its host, then `DB_HOST`, as Laravel merges them; an empty `host=` aborts the plan) is matched, case-insensitively and with an optional `.<network>` suffix naming a network the service joins (its real name, e.g. `nntmux_default`), against every name Docker DNS resolves to a service (service name, network alias, `hostname:`, container name, `links:` alias) and selects that service (which must be a data service); any other dotted name is external, and a name several services answer to aborts the plan. A selected database service must have exactly one replica (an external database leaves the default `mariadb` unchecked, rendered or not), and when it has no container it starts only after the writers stop, then is fenced by a fresh barrier.
- `just docker up` (or `just --justfile docker/Justfile up`) also routes existing app containers through the guarded deploy (including stopped containers after a failed migration); a stack with no app containers retains initial bringup.
- The first upgrade from an image without `tmux:drain` requires an authorized maintenance window and `DEPLOY_LEGACY_DRAIN=1 just deploy` (optionally `DEPLOY_LEGACY_DRAIN_TIMEOUT=3600`, default 1800 seconds). The streamed compatibility helper pauses dispatch, waits for the old monitor and finite workers to exit naturally, and restores prior runtime flags and the monitor on timeout or pre-stop failure. Unknown active panes and interactive consoles block the upgrade; close idle consoles only after checking they have no active jobs. Timeouts identify blocking roles without logging command arguments. Legacy IRC alone disconnects at final container stop; messages in flight have no replay guarantee during this one-time transition. No finite worker is force-killed by the bridge.
- During that first upgrade, the old scheduler is also frozen before waiting for its detached background workers. The helper requires Docker init, Linux pidfd support, Python 3.9+, and a readable dedicated cgroup PID counter; it fails closed if ownership cannot be verified. Once every finite scheduler worker has exited, Docker stops that frozen coordinator with a one-second timeout; only the idle coordinator can require forced termination, and it cannot admit another job during cutover. On an aborted drain, the helper restores its original running/stopped state. Subsequent images use cooperative drain. Without the explicit opt-in, old running images fail closed.
- If an interrupted first-upgrade attempt leaves a legacy scheduler barrier owned by an earlier operation, the deployment owner must first inspect the saved journal and verify authorization to recover that operation. Set `SCHEDULER_RECOVERY_TOKEN` to its exact recorded owning token, then restore under the same guard: `DEPLOY_BY=<owner> docker/bin/deploy-guard run resume-scheduler -- docker/bin/compose exec -T scheduler python3 - resume 0 "$SCHEDULER_RECOVERY_TOKEN" < docker/bin/legacy-scheduler-drain.py`. A tokenless resume deliberately leaves token-owned barriers intact. Preserve `COMPOSE_FILE` overrides, verify invocation source pins and exclusive signal authority, and inspect identity/restoration failures before retrying deployment. Old, intent-only or foreign-protocol journals remain unconfirmed and require investigation with the coordinator held; never edit or clear the journal, or signal a replacement PID, to bypass ownership and confirmation checks.
- Builds use the root Dockerfile's cached `base` target (`BASE_IMAGE`, default `nntmux/base:local`) and thin per-service targets (`selfhosted-web`, `selfhosted-horizon`, `selfhosted-scheduler`, `selfhosted-indexer`, plus `selfhosted` for all-in-one compatibility): system packages, PHP extensions, native libraries and locked dependencies are cached before application source. `.build.stamp` records per-service build fingerprints; a changed base image rebuilds every role image. A build stamps new image IDs only for the tags it built (`build-images` lists them in `.build.stamp.built`); every other role's tag must still name its recorded image, or the stamp fails and the next build plans again. `.deploy.stamp` and `.deploy.time` record only healthy rollouts: a full rollout succeeds only after all four app services are healthy on their expected images and no data or infrastructure container is stale (a targeted `DEPLOY_TARGETS` rollout updates the targeted service records while keeping `stale` on line 1 when other services still have pending changes), and it aborts before any change when an image tag was replaced after its build.
- Compose sends explicit `SIGTERM` through its init process; the indexer trap drains for `INDEXER_DRAIN_TIMEOUT=90` seconds within its 120-second stop grace. Horizon has 1920 seconds of stop grace to cover its 1860-second fingerprint supervisor timeout. The scheduler uses a Linux child-subreaper supervisor so detached background jobs remain owned and finish before container exit; its stop grace is also 1920 seconds. Deployment drains admitted work while web stays up, so active long jobs can delay rollout.
- Scheduler preflight uses `DEPLOY_SCHEDULER_DRAIN_TIMEOUT=1800` seconds; tune it through the deployment environment or `docker/.env`. In a current scheduler container, `python3 /app/docker/app/bin/scheduler.py drain --timeout=1800` pauses admission and waits for all owned background work. `restore` restores the state before that drain (used on deployment failure); `resume` explicitly reopens admission; `status` reports state and `check` verifies quiescence. The deployment helper pairs drain/restore with a unique operation token so recovery cannot undo an unrelated operator pause. A timeout or interrupted pending drain restores admission without killing finite jobs.
- Deployment builds only changed images while the old stack runs, probes the drain capabilities of the writers it will touch, stops Horizon first when it is affected (its active jobs finish while the scheduler and indexer keep queueing work), then drains the affected scheduler and indexer (`tmux:drain --timeout=900`, `DEPLOY_DRAIN_TIMEOUT`) — or every writer when migrations or stateful data services change — holds remote verification workers out with the new image's `releases:verification-barrier` when every writer stops (`DEPLOY_REMOTE_DRAIN_TIMEOUT`, default 900 seconds), stops only the drained/affected writers, runs migrations when required (including after any change to the database service, such as a storage cutover), then recreates only affected services and waits for health. Drain failure aborts before stopping writers/migrating and restarts Horizon; never bypass drain or stop unaffected data services. After a migration/health failure, repair under the same deployment ownership and retry; no automatic schema rollback. A barrier still running after a failed attempt keeps remote workers held; the next healthy rollout adopts and releases it, but only while the barrier fences the same database connection (a label on the barrier records it; host case is ignored, and a label from before that normalization is accepted for identical settings). A barrier container against another database, running, lost or stopped, aborts the rollout before anything removes it, as does an owed-release marker that records another database when no container is left; release that pause on its database by hand. A stopped database scheduled for rollout is started, like a missing one, before the barrier is taken. Any failed run that held a barrier records an owed release (`.deploy.stamp.barrier-owed`, holding the database's connection digest; an empty marker from older tooling with no barrier container left is refused while the rollout may switch databases), so the next run, even a no-op or selective one, takes a barrier and clears the durable pause without repeating a completed migration, and a failure before that rollout is healthy keeps the pause; a recreated MariaDB is fenced by a fresh barrier at once, kept on any later failure until the migrated rollout is healthy; if that fresh barrier cannot be taken, the just-started database is stopped again and the next run recreates it.
- Native and legacy indexer drains serialize control commands and pair deployment drain/resume with the same operation token. Abort recovery only releases a pause created by that deployment; an earlier operator pause remains intact. Direct operator `tmux:drain --resume` without a token retains explicit manual recovery semantics.
- Aborted drains restore the previous runtime flags and restart a previously live monitor after it exits. Recovery allows another 15 seconds for the monitor to exit naturally; if it remains stuck, report the restoration failure and keep scheduling paused. Investigate the monitor before retrying `php artisan tmux:drain --resume --session=nntmux` inside the indexer, or retry the opted-in guarded deployment for a legacy image. Never force-kill finite workers to bypass a failed drain.
- Treat production monitoring as read-only unless the user authorizes a specific operational change. Don't launch jobs, change NNTP/concurrency settings, restart, or deploy while observing.

### Master rollout procedure and evidence

- The deployment owner identifies the live runtime and exact Compose file list from the running container labels, fetches `xbmc4lyfe/newznab-tmux:master`, and integrates it into the candidate checkout without discarding local changes. Freeze the candidate source and effective configuration before the guarded rollout; a newer commit can wait for the next poll. A fetch, checkout update or image build alone does not deploy production.
- On each authorized poll, run `just deploy` (with `DEPLOY_BY=<session name>` in `docker/.env` or passed on the command line) from the candidate checkout with the runtime's approved absolute `COMPOSE_FILE` list, Compose project directory and shared guard/history paths. Retain the single owner and guard. Report a guard refusal, failed drain or recovery hold to the owner; do not repeatedly retry an unresolved failure or use `FORCE=1` to work around it. The one-time legacy transition above remains a separate readiness gate for running legacy images before routine cooperative rollouts are available.
- Measure change-to-healthy latency separately from attempt duration. Attempt duration is the outer `deploy result=started` to its matching `deploy result=finished` in `docker/.deploy.log`, including build and drain time. Report build, drain, migration and health timing separately when captured; do not infer missing phase timings. Cached builds reduce build time, while active finite jobs can still delay or abort a rollout. Claim a fast rollout only from measured end-to-end evidence.
- For a trailing-window report, state the cutoff and timezone, list each attempt's start, finish, candidate commit, duration and outcome, and identify attempts crossing the window boundary or still running. Count completed deployments separately from failed attempts, skipped/deferred polls and nested `build`/`up` entries. An exit-zero skip or defer is not a completed rollout, and neither is a `finished rc=0 (no service affected; stamped without a rollout)` attempt, which closes its `started` line without rolling anything out.
- Before reporting success, verify the deployment stamp, running image/source identity, all four app services' health, restored admission consistent with prior operator pauses, and resumed processing/progress. Use `.deploy.log` as the available deployment-history source; detailed Grafana reporting requires separately implemented and verified telemetry before it can supply evidence. A passing review, build or healthy old stack does not establish that the candidate was deployed, that backfill progress was preserved, or that the rollout was issue-free.
